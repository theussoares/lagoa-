# Verificação de segurança do MVP (2026-10-10)

Régua: [`SECURITY_RULES.md`](./SECURITY_RULES.md) (tiers e §37, política de bloqueio). Escopo: `apps/api`, BFF
(`apps/web/server`), config de produção, dependências e alertas de segurança do Supabase (projeto `lagoa-`).

## Veredito

**Nenhum bloqueante (Grave) encontrado.** O MVP pode seguir. Ficam pendências de tier Médio e Moderado,
nenhuma delas de bloqueio pela §37.

## O que foi conferido e está ok

- **Autenticação:** `SupabaseAuthGuard` global. Confere assinatura assimétrica via JWKS, emissor, audiência, `exp`
  e `sub` obrigatórios e `sub` UUID, e recusa conta anônima. Testes negativos cobrem os casos de token ruim. Só
  `health` e o hook de SMS são `@Public()`; o hook confere a assinatura Standard Webhooks sobre o corpo cru.
- **Autorização / IDOR:** toda rota com id do cliente é escopada pelo dono. `redemptions/:id` é filtrada por
  `loyaltyCards.customerId`. `visit-qrs/:id` e `:id/cancel` são filtradas por `shopId` do dono. O
  `counter/redemptions/:id/confirm` confere `redemption.shopId === loja do dono` dentro do `LedgerStore`.
  `wallet/cards/:shopId` é filtrada pelo usuário do JWT.
- **Mass assignment / validação:** body e param passam por `ZodValidationPipe` com schema do `shared`, e nenhum
  id de dono vem do cliente.
- **Injection:** só Drizzle (consultas parametrizadas). O `sql` cru encontrado não leva entrada do cliente.
- **XSS:** não há `v-html` nem `innerHTML` em código de produção.
- **CSRF:** cookie `httpOnly` + `SameSite=Lax` + `Secure` em produção, e `origin-guard` recusa escrita em `/api/**`
  sem `Origin` do próprio host ou da allowlist.
- **Erros:** `AllExceptionsFilter` devolve só `{ code }` e loga só o nome do erro, o código e a rota-padrão.
- **Dados pessoais:** celular cifrado no banco e mascarado na saída. Os logs não carregam celular nem token.
- **Segredos:** nenhum no repositório. As únicas credenciais versionadas são `postgres:postgres@localhost` de dev e CI.
- **Config de produção:** `EnvSchema` falha o boot sem `TRUST_PROXY_HOPS`, sem segredos de SMS, com
  `ENABLE_TEST_APPROVE=1` ou com `SUPABASE_URL` fora de https. A API usa `helmet` e CORS com lista explícita, sem
  credenciais.
- **Supabase:** RLS ligado e sem policy nas 12 tabelas, ou seja, nada sai pela API REST pública com a chave anon.
  É o desenho certo, porque só a API (Drizzle) acessa o banco. O alerta "leaked password" não se aplica: o login é só por SMS.
- **Rate limit:** registro, SMS (gate próprio), check-in, código curto, resgate, export e exclusão de conta. A
  validação do código de resgate no Balcão é `@FailClosedThrottle()`.

## Médio (corrigir logo depois do lançamento)

1. ~~**Lista de clientes do lojista sem `limit`.**~~ **Corrigido.** `GET /merchant/customers` agora devolve uma
   página de `MERCHANT_CUSTOMERS_PAGE_SIZE` (50), com `{ items, nextCursor, total, acceptingNotifications }`. O filtro
   (sumidos, prêmio liberado) e as contagens rodam no SQL, e só os celulares da página são decifrados. O cursor é o id
   do último cliente da página, validado como UUID, e um cursor de outra loja devolve página vazia. A tela Clientes
   ganhou "Carregar mais", e o Início usa o `total` do servidor. Testes: `customers.rules.test.ts`,
   `customers.service.test.ts`, `customers.http.test.ts` (inclusive cursor malicioso → 400),
   `customers.integration.test.ts` (Postgres: ordem, empate em microssegundos, nulos, filtros, contagens, cursor de
   outra loja), `merchantCustomers.nuxt.test.ts` e `mockCustomerPage.test.ts`.
2. ~~**`POST /check-in/code` não é fail-closed.**~~ **Corrigido.** A rota agora leva `@FailClosedThrottle()`. Teste de
   regressão em `check-in.http.test.ts`: com o contador fora do ar, o código curto recebe 429 sem consultar o banco,
   e o token de 256 bits continua passando.
3. ~~**Tentativas de verificação do OTP.**~~ **Corrigido** (o achado está abaixo; falta só conferir o painel).
   - **Conferido pelo banco e pelos logs do Supabase Auth:**
     - **Cadastro anônimo:** nenhuma conta anônima em `auth.users` (0 de 5; as 5 são por celular). Além disso, a API
       recusa token com `is_anonymous`.
     - **Tamanho do OTP:** 6 dígitos (`LOGIN_CODE_LENGTH`).
     - **Envio de SMS:** limitado por celular no hook (`SMS_SENDS_MAX_PER_WINDOW = 3` por 60 min, `sms_sends`).
   - **Achado:** o limite de verificação do Supabase é por IP, e o IP que ele vê é o do BFF na Vercel/AWS, que muda a
     cada chamada. O `POST /api/auth/verify` não tinha limite próprio, então quem chamasse o BFF várias vezes ganhava
     um pool de IPs para tentar acertar o código de 6 dígitos de um celular.
   - **Correção:** teto de `LOGIN_VERIFY_ATTEMPTS_MAX` (5) tentativas por celular a cada
     `LOGIN_VERIFY_WINDOW_MINUTES` (15 min).
     - **Onde é checado:** antes de chamar o Supabase, o BFF reserva a tentativa em `POST /v1/auth/login-attempts`.
       Essa rota é `@Public()`, mas só aceita quem apresenta o `BFF_SHARED_SECRET`.
     - **Contador:** fica no `rate_limits` (ADR-0002), com chave `login-verify:<hash do celular>`.
     - **Fail-closed:** se o contador cair, a API estiver fora ou faltar o segredo em produção, a tentativa é recusada.
     - **Configuração:** `BFF_SHARED_SECRET` passou a ser obrigatório em produção (já está no Vercel da API e do app).
     - **Testes:** `login-attempt-gate.test.ts`, `login-attempts.http.test.ts`,
       `login-attempt-gate.integration.test.ts` (duas instâncias sobre o mesmo Postgres) e
       `server/test/loginAttempts.test.ts`.
   - **Risco aceito:** quem sabe o celular de alguém pode gastar as 5 tentativas da pessoa e travar o login dela por até
     15 min. É o custo de qualquer teto por conta, e é bem menor que deixar o código ao alcance de tentativa e erro.
   - **Falta conferir no painel** (sem acesso pelo MCP):
     - Auth > Rate Limits: o limite de "token verifications".
     - Auth > Providers > Phone: a validade do OTP, que deve ficar baixa (ex.: 5 a 10 min).
     - Auth > Sign In / Providers: o cadastro anônimo desligado.

## Moderado (hardening)

4. ~~**Headers de segurança no app web.**~~ **Corrigido.** `apps/web` e `apps/site` mandam, em toda resposta
   (`routeRules['/**']`, constante única em `apps/web/server/utils/securityHeaders.ts`), CSP com
   `frame-ancestors 'self'`, `base-uri 'self'`, `object-src 'none'` e `form-action 'self'`, além de
   `X-Frame-Options: SAMEORIGIN`, HSTS de 2 anos, `nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` e
   `Permissions-Policy` (câmera só no próprio site, para o leitor de QR). Conferido no build de produção do app e no
   `config.json` gerado para o Vercel da LP. **Fica para depois:** `script-src` com nonce. O SSR do Nuxt põe o payload
   em `<script>` inline, então isso pede o `nuxt-security` ou um nonce próprio.
5. **Dependências (corrigido o que tem correção).** Por `overrides` no `pnpm-workspace.yaml`, cada um com o pacote que o
   puxa anotado para sair quando ele atualizar:
   - `esbuild` 0.27 (via `fontless`) → `^0.28.1`; `esbuild` 0.18 (via `@esbuild-kit/core-utils`, do `drizzle-kit`) →
     `^0.25.4`.
   - `simple-git` 3 (via `@nuxt/devtools` 3.x) → `^4.0.2`, o que também leva o `@simple-git/argv-parser` corrigido.
     A v4 só exporta `simpleGit` nomeado, então o devtools leva um patch de uma linha (`patches/`) que troca o import
     padrão pelo nomeado (funciona com a v3 e a v4).
   - `http-cache-semantics` (via `@swc/cli`) → `^4.3.0`.

   Conferido: `nuxt dev` com o devtools no ar, `simple-git` 4 lendo o repositório, `drizzle-kit generate` e `migrate`,
   build do app, da API (swc e Vercel) e da LP, typecheck e testes.

   **Ficam 2 alertas sem correção publicada** (`pnpm audit`):
   - `node-forge` ≤ 1.4.0 (via `listhen`): só gera o certificado do `nuxt dev --https`.
   - `braces` ≤ 3.0.3 (via `fast-glob`/`micromatch`): só lê padrões de glob do próprio projeto no build.

   Os dois são ferramenta de dev/build, nenhum roda no servidor de produção e nenhum recebe entrada de usuário. Rever
   quando sair versão corrigida.
6. ~~**Modo `mock` do painel.**~~ **Corrigido.** Com `NUXT_PUBLIC_MERCHANT_BACKEND=mock`, o servidor de um build de
   produção não sobe (`server/plugins/merchantBackendGuard.ts`). `pnpm dev`, os testes e o e2e continuam usando o mock.
   Conferido também no Vercel: nenhum ambiente define essa variável, então o padrão `http` vale.
7. ~~**Auditoria de eventos.**~~ **Corrigido.** Cada evento de segurança vira uma linha JSON com `type: "security"`
   (`shared/utils/securityEvent.ts`):
   - **BFF:** `auth.codeRequested`, `auth.login` (sucesso com o id da conta; falha com o código) e `auth.logout`.
   - **API (`AllExceptionsFilter`):** `access.unauthorized` (401), `access.denied` (403) e `rateLimit.hit` (429), com
     usuário quando há.

   Cada linha leva a rota-padrão e o `x-vercel-id`. Não entram celular, código, token, cookie, IP nem a URL real.
   Testes cobrem a ausência do celular mesmo quando ele está na URL.
